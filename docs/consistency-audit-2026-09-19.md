## 一、高优先级：用户可见行为与文档不符

### 1. 图片按尺寸搜索失效——而且这是 HEAD 引入的回归（最严重）

- **言论**：`CHANGELOG.md:30`「图片条目（按尺寸、来源或备注）现已全面支持即时搜索」；`CLAUDE.md`「元数据字段（label、custom_label、source_name）跨文本与图片条目统一做 LIKE 子串匹配」。
- **行为**：
  - 图片行的 `label` 列**从不落库**——`src/db/crud.rs:242-259` 的图片 INSERT 只绑定 `custom_label`，没有 `label`；
  - 界面上的「Image (W×H)」是读取时合成的：`src/types.rs:113 format!("Image ({width}×{height})")`；
  - Rust 元数据检索只 LIKE 数据库列：`src/db/search.rs:108-114 WHERE label LIKE ?1 OR custom_label LIKE ?1 OR source_name LIKE ?1`；
  - Swift 侧已不再补 `label`：`SwiftApp/Popup/HistoryPopupContent.swift:536-541` 只补 `matchIds` 与 `DayGroup` 日期标签。
- **关键因果**：HEAD `6787f76` 删掉了本地匹配 `$0.label.localizedCaseInsensitiveContains(query)` 等三行，而被删代码旁边的原注释正是「images are findable only via their generated label ("Image (WxH)") / source name」。旧路径能搜到尺寸，新路径不能。
- **活库实测**：`select entry_type, count(*), sum(label!='') from clipboard_history group by entry_type` → `1|218|0`（218 张图片，label 全空）；把代码里那条元数据 SQL 原样跑一遍，`label|custom_label|source_name LIKE '%1080%'` 命中 **0** 行，而库中存在 `282×270`、`1272×666` 等图片。
- **结论**：按尺寸搜图片**搜不到**；承诺与行为相反，且是对 HEAD 之前行为的回归。GUI 未驱动，但执行的 SQL 已在活库上复现。

### 2. 预览解码「2048px 上限」实际是下限

- **言论**：`CLAUDE.md:133`「预算 = 显示尺寸×scale 与 2048px 的较小值」。
- **行为**：`SwiftApp/Backend/ImageDecode.swift:57 zoomHeadroomPx = 2048`，`ImageDecode.swift:71-78` 返回
  `min(max(width, height), max(Int(displayLongest * scale), zoomHeadroomPx))`。
  `max(..., 2048)` 使 2048 成为**地板**；真正的规模是「显示尺寸×scale」。
- **运行态**：日志 `preview_decode … max_dim=` 出现 `2066/2134/2160/2214/2226/2244/2286/2293(×42)/2309/2348`，**普遍 > 2048**。
- **结论**：文档把上限与下限写反了；这条直接关系到预览峰值内存的预期。

### 3. 「大图走 clipboard_get_image_full_by_db_id（优先内存，后备 DB）」两项都不成立

- `CLAUDE.md:133` 的这句话有两处与执行代码不符：
  1. `src/ffi/accessors.rs:31-65` 该导出**只有** `SELECT png_data`，没有任何内存层（同一处的注释 `accessors.rs:28` 也自认「Load full image directly by database row id」）；
  2. 预览根本不走它——走的是 `clipboard_decode_preview_by_db_id`（`ImageDecode.swift:116`，Rust `accessors.rs:141-157`）；`getImageFullByDbId` 只用于 GIF 兜底（`ImageDecode.swift:122`）与右键「复制图片」。

### 4. 缩略图缓存容量：README 与代码不一致

- `README.md:78`「10MB 缩略图缓存」；代码 `SwiftApp/ClipboardBackend.swift:134-135 countLimit = 120 / totalCostLimit = 8 * 1024 * 1024`（8 MB），`CLAUDE.md:133` 写的也是 8MB。README 与实现及各文档之间不自洽。

### 5. 设置面板标签页数量

- `CLAUDE.md:121`「5 标签页设置面板」；`SwiftApp/Settings/InlineSettingsView.swift:99 tabTitles = ["通用","快捷键","存储","忽略","许可证","关于"]` → **6** 个。

### 6. 全局快捷键与辅助功能权限

- **言论**：`README.md`「两种机制…两者都需要 macOS「辅助功能权限」」；设置页 `InlineSettingsView+GeneralTab.swift:33`「应用需要辅助功能权限才能使用全局快捷键和自动粘贴」。
- **行为**：`HotkeyManager.swift:153-172` 的 Carbon `RegisterEventHotKey` **不以** `AXIsProcessTrusted` 为前置；只有 Carbon 注册失败且 `!axTrusted` 时才提示冲突（`HotkeyManager.swift:180-189`），注释也自认「NSEvent global monitor cannot see keys without Accessibility」。
- **结论**：需要辅助功能的只有 Cmd+V 模拟与 NSEvent 后备；「全局快捷键需要辅助功能」对 Carbon 主路径是错的。粘贴需要权限这一条为真（`src/ffi/paste.rs:141`）。

### 7. 更新下载顺序：注释与 README 与代码相反

- **言论**：`InlineSettingsView.swift:40`「(GitHub first, lanzou fallback)」；`README.md:39`「自动检查更新（GitHub Releases）」。
- **行为**：`SwiftApp/Update/UpdateDownloader.swift:107-115` 先 `downloadFromLanzou`，失败才 `downloadFromGitHub`（注释亦自述 primary=蓝奏云）；`SwiftApp/Update/` 整个目录在 `CLAUDE.md` 的 Swift 目录树中缺失。

### 8. 「忽略密码与敏感内容」的宣称覆盖面大于实现

- `InlineSettingsView+IgnoreTab.swift:395` 文案点名「1Password、Bitwarden、钥匙串」；`src/macos.rs:97-98` 注释点名「1Password, Bitwarden, KeePassXC, Apple Keychain」。
- 实际白名单只有 4 个：`org.nspasteboard.ConcealedType / AutoGeneratedType / TransientType / com.agilebits.onepassword`（`src/macos.rs:122-127`）。Bitwarden/钥匙串只能靠标准 Concealed 类型**间接**命中；文档把「间接」写成了显式覆盖。

## 四、代码内部契约被违反（潜在，本次未触发）

1. `src/ffi/history.rs:548-558`：注释承诺「DELETE 没删掉的条目保留在列表里」，但紧接的 `while hist.len() > cleanup_threshold { hist.pop() }` 会**丢掉 DB 行仍然存在**的尾部条目 → 重启后「复活」。触发条件：总条数 > `cleanup_threshold/0.6`（默认 3000 → 需 >5000 条）后点「清理最旧 40%」。当前库 1215 条，未触发。
2. `src/ffi/paste.rs:332-370`：DB 写入失败只记日志，随后仍把条目移到内存顶部并返回 pid>0 → 快捷键照发、内存条目 `db_id=0`、DB 无行（重启即丢）。属于「继续执行错误路径」，与全仓「主流程失败显式暴露」的约定不一致（同文件 `monitor.rs:448-476` 的捕获路径是正确回滚的）。
3. `src/backend.rs:32/35` + `ffi/history.rs:152-168`：撤销载荷 >48 MB 时先写盘、随即被 `push_deleted` 淘汰，`delete` 仍返回成功——撤销已不可能但调用方以为可以。

## 六、仪表自检（值得单独说）

`python3 perf/analyze.py /tmp/copyattach_debug.log --session-start 1789778514362` → **Verdict: INVALID**。

- 9 条门禁中 8 条 PASS，`G4_clock` **FAIL**（slope ratio 1.1105，R² 0.949281，621 samples）。
- 物理原因可对账：同一 pid 的 `t`（单调）从 `216334004172250` 到 `218447168761750` 走了 **2113 s**，而 `wall` 走了 **3061 s**——日志中 09:14:32→09:24:08 有 ~9.5 min 空档，机器中途睡眠，`mach_absolute_time` 不含睡眠。
- 结论：**本次会话的延迟数字不可用作证据**（`popup.show p95 90 ms` 等一律不采信）。仪表按设计拒绝下结论，这一点是言行一致的。同时也说明：任何「实测」结论都必须先看这台机器是否中途睡眠。

## 七、结论

- **核心数据流是言行一致的**：捕获（500ms/changeCount/write-through）、图片两阶段、FTS 上限与兜底、entry_id/db_id 不变量、撤销栈 ≤1、启动不读剪贴板、粘贴权限门禁、签名与版本注入——都能在运行态复现，未发现「注释说 A、实际做 B」的核心路径。
- **真正的问题分三类**：
  1. **功能性回归（最严重）**：HEAD `6787f76` 把元数据检索搬到 Rust 时，删掉了 Swift 侧按显示 label 的本地匹配，而图片的 `label` 从来没有落库 → 图片按尺寸搜索失效，与 CHANGELOG/CLAUDE.md 的承诺相反。
  2. **CLAUDE.md 对图片加载/预览的描述已过时**：`优先内存，后备 DB` 不存在、`2048px 上限` 实为下限、`get_image_full_by_db_id` 并非预览入口。
  3. **注释腐蚀**：11 处注释与相邻代码相反（尤其 `ffi/search.rs`、`HistoryPopupContent` 的三处、`ClipboardBackend` 的 0.5s 轮询），加上目录树/计数与标签页数量失真；README 与 CLAUDE.md 在缓存大小、空闲内存上互相矛盾。
- **未实测（只能标为假设）**：许可证「误删钥匙串自动换绑不占座位」（服务端行为，仓库内无证据）、永久许可证「无任何周期定时器」（代码确定，日志未观察到 perpetual 分支）、拖拽/切标签的视觉行为（未驱动 GUI）、`trim_oldest_percent` 复活（需 >5000 条才可达）。
